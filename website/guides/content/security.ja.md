# TianShanOS セキュリティ ページ ガイド

このガイドでは、TianShanOS 0.6.1 の機能とインターフェイスについて説明します。これらの機能が変更されていない今後のバージョンでも引き続き役立つ可能性があります。バージョン番号が変わっても、ガイドが自動的に廃止されるわけではありません。インターフェイス、手順、または結果メッセージが異なる場合は、続行する前に、インストールされているバージョンのリリース ノートを確認してください。

このガイドを使用して、デバイスのパスワードの変更、SSH アクセスの設定、サーバー ID の確認、および証明書の管理を行います。初めてセットアップする場合は、第 1 章、第 2 章、および第 3 章から始めてください。証明書と Config Pack の手順は、これらの機能を担当する管理者を対象としています。

> 信頼できる管理ネットワークを使用します。現在、完全な Web インターフェイスは HTTP を使用しており、ほとんどの API 操作には一元化されたログインと権限の適用がありません。デバイスを制御された管理ネットワーク上に置きます。 HTTPS 証明書をインストールしても、完全な Web インターフェイスは HTTPS に切り替わりません。

## 1. 始める前に

### 1.1 必要なタスクを見つける

| タスク | どこへ行くか |
|---|---|
| デバイスの root または admin パスワードを変更します | アカウントのセキュリティ;第2章 |
| SSH キーを使用してサーバーに接続します | キー管理とデプロイされたホスト。第3章 |
| キーをコピーするか、サーバーの ID を確認します | キー管理と既知のホストのフィンガープリント。第4章 |
| 証明書と相互認証のセットアップ | HTTPS 証明書;第5章 |
| Exchange 暗号化構成パッケージ | Config Pack;第 6 章 一般的な設定アプリケーションはまだ完了していません |

### 1.2 アカウントとデバイス ID

- **admin** は、セキュリティを開いてキー、ホスト、証明書、および Config Pack コントロールを表示できますが、アカウント セキュリティは表示できません。
- **root** は、root および admin パスワードを設定したり、admin をデフォルトのパスワードにリセットしたりすることもできます。これらのパスワード管理操作では、root 承認をチェックします。
- **Developer デバイス** は、デバイス証明書の組織単位 (OU) によって識別されます。これはデバイス ID です。現在、構成パックと SSH ホスト構成をエクスポートできるのはこれらのデバイスのみです。 root としてサインインしても変更されません。

表示されるボタンは、その API がアクセス許可を強制することを確立しません。認証自体をチェックするパスワード管理などの操作とは別に、アクセスは現在、信頼できる管理ネットワークを通じて制限する必要があります。

### 1.3 操作の準備

1. ブラウザの IP アドレスが目的のデバイスに属していること、およびコンピュータが信頼された管理ネットワーク上にあることを確認してください。
2. SSH のアドレス、ポート、ユーザー名をサーバー管理者に確認してください。
3. ページを通じて公開キーを展開または取り消すには、リモート アカウントのパスワードとパスワード認証が必要です。サーバー管理者は、その後パスワード認証を有効にしておくかどうかを決定します。
4. アクセスの取り消し、キーの削除、または証明書の置き換えを行う前に、別の管理接続 (サーバー コンソール、別の管理者キー、またはデバイスの HTTP インターフェイス) が機能していることを確認してください。

## 2. デバイスのパスワードを変更する

これらのコントロールは、TianShanOS ログイン パスワードを変更します。リモート サーバー上の SSH パスワードは変更されません。

### 2.1 最初のサインイン後のプロンプト

アカウントがまだパスワードが変更されていないとマークされている場合は、サインイン後にパスワード変更プロンプトが表示されます。長くてユニークなパスワードを設定します。後で変更することを選択すると、パスワードを変更せずにプロンプ​​トが閉じられます。

このプロンプトは、いつでも再度開くことができるアカウント設定画面ではありません。 admin がすでにパスワードを変更しており、さらに変更する必要がある場合、root はセキュリティからパスワードを設定できます。

### 2.2 パスワードを root として設定します

1. root としてサインインし、ナビゲーション バーで [セキュリティ] を開きます。
2. [アカウント セキュリティ] で、root または admin のパスワード コントロールを見つけます。新しいパスワードとその確認を入力します。
3. [root パスワードを設定] または [admin パスワードを設定] を選択します。インターフェイスは 4 ～ 64 文字を受け入れます。 4 文字は技術的な最小値です。長くて一意のパスワードを使用してください。

**結果を確認してください:** 元のセッションからサインアウトする前に、プライベート ブラウジング ウィンドウで新しいパスワードを使用してサインインします。新しいパスワードを設定しても、既存のセッションは自動的に終了しません。

**サインインが失敗した場合:** まずアカウントとデバイスのアドレスを確認してください。試行が 5 回連続して失敗すると、約 5 分間のロックアウトがトリガーされます。推測を繰り返すことは避けてください。

### 2.3 admin パスワードのリセット

Root は、[admin をデフォルトにリセット] を選択して、パスワードを `rm01` に復元し、ログイン ロックアウトをクリアできます。新しいセッションで admin としてサインインし、直後に一意のパスワードを設定します。

> デフォルトのパスワードは、アクセスを一時的に回復する場合にのみ使用してください。すぐに変更し、不要になったセッションからサインアウトしてください。

## 3. SSH キーを使用してサーバーに接続します

初期セットアップでは、RSA キーを作成し、その公開キーを展開し、結果を確認して、接続をテストします。このプロセスの一環としてサーバーのフィンガープリントを確認します。キーを廃止する場合は、最初にすべてのサーバーでアクセスを取り消し、古いキーが機能しなくなったことを確認してから、デバイスから削除します。

### 3.1 キーの作成

1. [キー管理] で、[新しいキーの生成] を選択します。
2. `backup01` など、未使用のキー ID を選択します。英文字と数字の短い組み合わせを使用し、カンマを含まず 10 文字以内で使用します。実際の制限は 10 UTF-8 バイトです。非 ASCII 文字はそれぞれ複数バイトを使用できます。
3. RSA 2048 または RSA 4096 を選択します。 RSA 2048 がデフォルトです。 ECDSA オプションが表示されますが、現在の SSH ワークフローはそれらをサポートしていません。 SSH には RSA を選択します。
4. 役立つ場合は、コメントまたはエイリアスを追加します。秘密キーをバックアップまたは移行する必要がある場合にのみ、「エクスポート可能」をオンにします。このオプションを後で変更するためのページ コントロールはありません。
5. 必要に応じて [非表示] を設定し、[生成] を選択します。このオプションはリスト表示に影響します。実際のキー ID は秘密にされません。

**結果を確認してください:** 完了後、ウィンドウが閉じてリストが更新されます。目的の ID と RSA タイプを見つけて、公開キーを開きます。完全なテキストが `ssh-rsa` で始まることを確認します。

**生成を待っている間：**再度送信しないでください。ウィンドウを閉じても、デバイス上の生成処理は取り消されません。

| メッセージまたは状況 | どうすればいいですか |
|---|---|
| IDはすでに使用されています | 別の ID を選択してください。新しいキーのワークフローは、キーを上書きするのではなく、既存の ID を拒否するようになりました。 |
| キー数の制限に達しました | SSH の鍵は最大 8 件保存できます。使っていない鍵を減らす場合は、先に失効の手順を行ってください。 |
| ストレージまたはメモリが不足しています | 再試行する前に、デバイス リソースの問題を解決してください。失敗を成功した作成として扱わないでください |
| キーは生成されましたが、リストを更新できませんでした | 手動で更新してキーを確認してください。再度生成しないでください |
| 世代は未確認 | デバイスはまだ動作している可能性があります。待って記録を確認してください。同じIDを再送信しないでください |
| クリーンアップが完了しませんでした | デバイスのストレージを確認し、必要に応じて管理者に協力してもらい、それ以降のキーの作成を一時停止します |

同じ ID を持つレコードの検索は、レコードが存在することのみを証明します。結果が未確認の場合は、操作が完了したものとして扱う前に、それが意図したキーであることを確認してください。

### 3.2 公開キーの展開

デプロイメントでは、公開キーがリモート アカウントの `~/.ssh/authorized_keys` に追加され、そのアカウントが一致する秘密キーを受け入れることができるようになります。サーバーのパスワードは変更されません。

1. 目的のキーの行で [デプロイ] を選択します。
2. サーバー アドレス、ユーザー名、SSH ポート、および SSH ログイン パスワードを入力します。
3. アドレスとアカウントを確認し、[展開の開始] を選択します。
4. 結果を読み取り、「デプロイされたホスト」の下の対応するレコードを確認します。

> 新版では、パスワード認証の前にホストのフィンガープリントを確認します。登録済みホストの値が変わっている場合は接続を拒否します。ただし、初回の公開鍵の配備では、未登録ホストの値を確認なしで保存して信頼します。初回は管理されたネットワークで行い、信頼できる別の経路でフィンガープリント全体を照合してください。

### 3.3 導入結果の理解

| 結果からわかること | 次に何をするか |
|---|---|
| キーが展開され、ホストが登録され、公開キーのサインインが検証されました | ホストの詳細を確認し、実行する必要がある実際のタスクをテストします |
| キーはデプロイされ、ホストは登録されましたが、サインインは未確認です | [テスト] を選択します。失敗した場合は、別の管理接続を介してリモート認証とアカウント設定を確認してください |
| キーはデプロイされましたが、登録が失敗したか、未確認です | 再度展開する前に、ローカル リストとリモート認証を確認してください |
| デプロイは完了しましたが、リストを更新できませんでした | 手動で更新してください。リストの更新が失敗しても、リモート キーがインストールされていないことを意味するわけではありません |

**結果が不完全であるため、繰り返しデプロイしないでください。** デプロイごとにキーが追加され、重複したエントリが作成される可能性があります。リモート結果を確認する必要がある場合は、別の管理接続を使用して `authorized_keys` を検査します。

### 3.4 接続をテストする

1. [展開されたホスト] で、アドレス、ポート、ユーザー名、およびキー ID を確認し、[テスト] を選択します。
2. ホスト フィンガープリントの確認が表示された場合は、[信頼して接続] を選択する前に、セクション 4.3 の説明に従って信頼できるフィンガープリントを取得して比較します。
3. 接続後、デバイスは固定エコー コマンド `echo "TianshanOS SSH Test OK"` を試行します。

**成功の意味:** テスト ページでは、リモート コマンドの終了ステータスや出力ではなく、リクエストが成功したかどうかを引き続きチェックします。基本的な接続チェックとしてご利用ください。重要なタスクの場合は、実際の出力、終了ステータス、および権限を確認してください。このテストでは、sudo または他のアプリケーション コマンドが機能するかどうかも確認されません。

**失敗した場合:** 接続、SSH サービス、アカウント、およびリモート公開キー認証を確認してください。フィンガープリントが変更された場合、またはサーバーの ID が不明な場合は、再試行を停止します。

### 3.5 ローカルキーを削除する前にアクセスを取り消す

1. 別のサーバー管理接続が機能していること、および元のキーがデバイス上に残っていることを確認します。
2. ホスト行で [取り消し] を選択し、サーバーのパスワードを入力し、[取り消しと削除] を確認します。キー行から開始してターゲットの詳細を入力することもできます。
3. 結果を読み取り、信頼された接続を使用して、公開キーと重複が `authorized_keys` から削除されていることを確認します。古いキーが機能しなくなったことを確認します。
4. 取り消しでは、`authorized_keys.bak` バックアップが残ります。後で古い認証が復元されないように、サーバーのバックアップ ポリシーに基づいて処理してください。
5. ローカルホストレコードが削除されたことを確認します。ページはこのリクエストをチェックします。リモートの取り消しは成功したが、ローカルの削除は失敗した場合は、ローカルのクリーンアップを更新して個別に処理します。
6. すべてのターゲット サーバーが処理された後でのみ、古いキーと不要な秘密キーのコピーを削除する必要があります。

**一致する公開キーが見つからない場合:** ローカル レコードのみの削除を選択する前に、アカウントが正しいこと、およびキーがサーバー上にないことを確認してください。

**ホストを削除できない場合:** サービスがレコードを使用または保護している可能性があります。 SSH コマンドまたは関連する自動設定でサービスのステータスと参照を確認してください。サービスの停止または参照の解決を完了してから、再試行してください。不明な状態は管理者に確認してください。

**失効が失敗を報告した場合:** どのステップが失敗したかを特定します。ローカルのクリーンアップが失敗した場合でも、リモート キーがすでに失われている可能性があります。サーバーの承認と実際のサインイン チェックを使用して、リモート結果を確立します。この問題が解決されるまで、ローカル キーを保管してください。

## 4. キー、ホスト、指紋の管理

### 4.1 公開キーのコピーまたは秘密キーのエクスポート

**公開キー:** 公開キーを選択し、サーバー管理者用の完全な単一行の値をコピーします。これは公開資料です。間違った人に送信しても秘密鍵が公開されることはありません。管理者がアカウントの承認リストにアクセスを追加すると、アクセスが許可されます。

**秘密キー:** エクスポートは、作成時にエクスポート可能が有効になっている場合にのみ使用できます。信頼されたコンピューターと分離された管理ネットワーク上の秘密キーを選択します。承認されたシークレット ストアに保存し、一時クリップボードをクリアしてコピーをダウンロードします。チャット、チケット、ログには決して貼り付けないでください。

**コピーで何も行われない場合:** ブラウザによって、HTTP ページのクリップボード アクセスが制限される可能性があります。テキストを手動で選択してコピーし、境界マーカーと完全性を確認します。コピーを可能にするためにブラウザのセキュリティ設定を弱めないでください。

### 4.2 取り消し、削除、および削除

| アクション | 効果 |
|---|---|
| 公開鍵を取り消す | サーバーの承認を削除しようとします。リモートパスワードが必要です |
| ホストを削除します | サーバーアクセスを取り消さずにローカル接続レコードを削除します |
| キーを削除します | サーバーに接続したりアクセスを取り消したりすることなく、ローカルキーマテリアルを削除します |
| ホストのフィンガープリントを削除します | 接続レコードやリモート認証ではなく、保存されたサーバー ID レコードを削除します |

デプロイされたホストはローカル リストであり、サーバー認証のライブ ビューではありません。空のリストはアクセスが削除されたことを証明するものではなく、リストされたホストに到達できるかどうかは保証されません。

### 4.3 SSH サーバーのフィンガープリントを確認する

フィンガープリントは、接続先のサーバーを識別します。このページには、SHA-256 ダイジェストが 64 個の 16 進文字として保存されます。 OpenSSH ツールでは通常、`SHA256:base64` が表示されます。比較する前に、同じ形式について管理者に問い合わせてください。文字列を直接比較することはできません。

**初期展開後:** [既知のホスト フィンガープリント] で [表示] を選択し、完全な値をサーバー コンソール、資産インベントリ、または別の信頼できるチャネルから取得した値と比較します。この表には最初の 32 文字のみが表示されていますが、これでは完全なチェックには不十分です。

**テストが確認を求める場合:** ダイアログには現在の完全なフィンガープリントが表示されます。 [信頼して接続] を選択する前に、個別に検証してください。変更されている場合は、サーバー ID、IP、ポート、および保守記録も確認してください。ダイアログが表示されたからといって承認しないでください。

**フィンガープリントが異なる場合、またはそのソースが不明な場合:** 接続をキャンセルして調査してください。以前に信頼できない接続上でパスワードを使用したことがある場合は、そのパスワードが漏洩する可能性があるものとして扱います。信頼された接続を通じて変更し、サインイン ログを確認して、不要な承認を削除します。アクセスを取り消すために、不審な接続を通じてパスワードを送信しないでください。

**承認された再構築またはホスト キーの変更後:** まず、新しい完全なフィンガープリントとメンテナンス レコードを確認してください。確認したら、[テスト確認] ダイアログでそれを受け入れます。あるいは、古いエントリを削除し、再度テストして、検証されたフィンガープリントを確認します。テスト パスには明示的な確認が必要になりました。再接続すると新しいキーが自動的に信頼されるとは考えないでください。

**SD カードを保護します:** 既知のホストのフィンガープリントは、カード上のプレーンテキスト JSON に同期されます。起動時に、利用可能な SD フィンガープリント構成が、対応するローカル レコードを置き換えます。これらのファイルは署名されていません。信頼できない変更を許可しないでください。

### 4.4 SSH ホスト構成のインポートとエクスポート

この専用の `.tscfg` ワークフローには、アドレス、ポート、ユーザー名、認証タイプ、キー ID が保存されます。 SSH パスワードや秘密キーは含まれておらず、リモート アクセスは許可されません。これは、第 6 章の未完了の一般出願とは別のものです。

**エクスポートするには:** Developer デバイスで、ホスト行の [エクスポート] を選択します。別のデバイスの場合は、その証明書を指定して検証し、パッケージを生成して、[ダウンロード] を選択します。ファイルが保存されたことを確認します。通常のデバイスはコントロールを表示できますが、そのエクスポート要求は拒否されます。

**インポートするには:**

1. パッケージがこのデバイス用に作成されたこと、SD カードが書き込み可能であること、ソースが信頼されたチャネルを通じて検証されていることを確認します。
2. このデバイスに正しい参照キーがあることを確認してください。 ID が一致するだけでは不十分です。キーマテリアルはサーバーの認証と一致する必要があります。
3. [ホストのインポート] を選択し、ファイルを選択して、プレビューを確認します。構成を同じ名前で置き換える場合にのみ、上書きを有効にします。
4. プロンプトに従って確認して再起動します。インポートでは、まずパッケージが SD カードに保存されます。再起動時にロードと復号化が試行されます。
5. スタートアップのロードが完了するまで待ち、ホスト リストを更新し、アドレス、アカウント、ポート、キーを確認してからテストします。

プレビューに成功しても、署名元が信頼できることや、このデバイス宛てのパッケージであることは確認できません。受信側のフィンガープリントは読み込み時に確認されます。起動時にはホスト設定が統合され、関係のないローカル記録は残ります。1 つのパッケージをインポートしても、既存の一覧全体は消えません。

間違ったレコードを削除し、対応する SD 設定がクリアされていることを確認します。残りのパッケージは、再起動後に再度ロードできます。レコードが使用中の場合は、サービス参照を解決します。デバイス証明書を置き換える前に、セクション 5.6 もお読みください。

## 5. HTTPS 証明書と mTLS を構成する

ポート 443 上の現在のサービスは、完全な Web インターフェイスではなく、ヘルス、アイデンティティ、および権限テストのエンドポイントを提供します。デフォルトの起動には、デバイス キー、デバイス証明書、クライアント CA チェーン、および有効なデバイス クロックが必要です。

### 5.1 どの証明書が何を行うかを知る

- **デバイス証明書と秘密キー**により、デバイスはクライアントにその身元を証明できます。
- **クライアント証明書と秘密キー**は、コンピューターまたはサービスによって保持され、クライアントがデバイスに対して身元を証明できるようにします。
- **デバイス上のクライアント検証 CA** がクライアント証明書を検証します。コンピュータまたはブラウザがデバイス証明書を自動的に信頼するようにはなりません。

この双方向認証は、相互 TLS または mTLS と呼ばれます。クライアントは、デバイス証明書の発行元 CA を信頼し、そのアクセス名、許可された用途、有効性を確認する必要があります。

### 5.2 ステータスの読み取りとデバイスの時刻の設定

保存済み、有効期間内、および HTTPS: 実行中 は、ストレージ、有効期限、およびサービスの動作を個別に説明します。一方が他方を確立するわけではありません。

| ステータスまたは状況 | どうすればいいですか |
|---|---|
| デバイス証明書、秘密キー、またはクライアント検証 CA がありません | 次のセクションを使用して、不足している認証情報をインストールします。 |
| デバイス時間の待機中 | コンピューターの時計が正しいことを確認し、[このコンピューターからデバイスの時刻を設定する (ブラウザー ソース)] を選択します。 |
| まだ有効ではないか期限切れです | デバイスの時計と証明書の日付を確認します。有効期限が切れた場合は更新を手配する |
| 有効期間内ですが、HTTPS が実行されていません | 表示された認証情報の欠落、キーの不一致、または起動エラーを読み取ります。それを解決してリフレッシュする |
| 実行中のサービスはまだ以前の資格情報を使用しています | 他の作業を保存し、デバイスを再起動します。新しい認証情報が起動要件を満たしており、使用されていることを確認します。 |
| ストレージまたはステータスが未確認です | 更新して確認してください。指示に応じて再起動します。インストールや削除を繰り返さないようにする |

時刻設定後、表示される機器の時刻と同期状態を確認してください。サービスが実行されていない場合、システムは資格情報と時間の要件が満たされると起動を試みます。停止したままの場合は、インストールが準備ができている証拠として扱うのではなく、表示された理由を調査してください。

### 5.3 デバイスキーと証明書リクエストの生成

1. [キー ペアの生成] を選択します。これにより、SSH キーとは関係のない、別の ECDSA P-256 秘密キーが作成されます。このインターフェイスを介してエクスポートすることはできません。
2. キーがすでに存在する場合は、最初にセクション 5.6 を読んでください。続行すると上書きされます。
3. [CSR の生成] を選択します。デバイス ID (CN)、組織、部門を入力するか、すべてのフィールドを空白のままにします。部門は、証明書の組織単位 (OU) に対応します。
4. [証明書署名要求の生成] を選択し、完全な CSR テキストを CA 管理者に送信します。

**短く安定したデバイス ID を使用してください。** 英語の文字と数字を 63 バイトの UTF-8 制限内に収めるのが最も簡単です。非 ASCII 文字は複数バイトを使用できます。インターフェイスが長さエラーを報告する場合は、フィールドを短くします。

**発行前に名前を確認してください:** カスタム フィールドのパスは SAN を生成しません。すべてのフィールドが空白の場合、CN は `TIANSHAN-DEVICE-001` に固定されます。現在の IP は、利用可能な場合にのみ IP SAN として追加されます。 DNS SAN は追加されません。 CA 管理者に、制御された発行プロセスを使用して、実際の IP 名または DNS 名と必要な認証目的を最終証明書に含めるよう依頼します。このフォームでは SAN を編集できません。

CSR には秘密キーが含まれておらず、証明書もインストールされません。発行前に CA 管理者に公開キー、サブジェクト、および SAN を検査してもらいます。

### 5.4 デバイス証明書のインストール

1. 現在のデバイスの秘密キーと一致する PEM 証明書を取得します。
2. [証明書のインストール] を選択し、境界マーカーを含む完全なテキストを貼り付けて、[インストール] を選択します。
3. 保存された結果、証明書の有効性、および実際の HTTPS ステータスを確認します。件名、発行者、日付を確認します。

インストールでは、形式とキー ペアがチェックされます。新しいステータス表示では、時間の有効性と起動要件も報告されますが、クライアントは依然として信頼チェーン、アクセス名、および許可された使用を検証する必要があります。

キーが一致しない場合は、現在の CSR に対して発行された証明書を見つけます。エラーをクリアするために秘密キーを再生成しないでください。結果が未確認の場合は、更新して保存内容を確認してから、再試行するかどうかを決定します。

### 5.5 クライアント CA チェーンをインストールしてテストする

1. [CA のインストール] を選択し、クライアントを信頼するために使用される 1 つ以上の PEM CA 証明書を貼り付け、[インストール] を選択します。
2. 状態を確認してください。停止したサービスは、資格情報と時間が準備できると起動を試みます。実行中のサービスが資格情報の変更を報告した場合は、指示に従って再起動して資格情報を適用します。
3. 正しい目的と役割を持つ信頼できるクライアント証明書を使用して、適切なテスト エンドポイントにアクセスします。
4. 信頼できない証明書を使用するか、証明書を使用せずに繰り返し、拒否を確認します。

**結果を確認してください:** HTTPS は実行されており、目的の証明書を使用しています。アクティブな証明書 SHA-256 が表示されている場合は、そのフィンガープリントを比較します。信頼できるクライアントは、その役割が許可するエンドポイントにのみアクセスする必要があります。信頼できないクライアントは接続しないでください。これらの結果を実機で確認してください。

### 5.6 証明書を更新するか、すべての資格情報を削除します

**証明書の有効期限:** 侵害されていないキーを再利用して新しい証明書を要求し、インストールし、ステータスの指示に従って適用し、再度テストします。構成パックは、受信者の証明書のフィンガープリントに関連付けられます。同じキーを使用している場合でも、証明書が変更されているため、再初期化または再起動後に古いパッケージが拒否される場合があります。事前に交換用パッケージを手配してください。

**秘密キーの交換:** 古い CSR と証明書は新しいキーと一致しなくなります。これにより、CA で古い証明書が取り消されることはありません。公開されたキーは CA 管理者と個別に処理してください。紛失したキーに依存するパッケージは回復できない場合があります。

**すべての資格情報を削除:** 資格情報を削除すると、デバイス キー、デバイス証明書、およびクライアント CA チェーンが一緒に削除されます。 HTTP 管理アクセスが機能することを確認し、最初に交換パッケージを手配します。公開証明書のバックアップでは秘密キーを復元できません。

削除後、デバイス証明書がないか、資格情報が欠落していないかを確認します。実行中の HTTPS サービスは、以前の資格情報を保持している可能性があります。保存されたデータを削除しても、すぐに取り消されるわけではありません。指示に従って再起動し、古い認証情報が使用されていないことを確認します。新しいキー、発行されたデバイス証明書、クライアント CA チェーン、および接続テストを使用してサービスを復元します。

## 6。 Config Pack の制限を理解する

Config Pack は、暗号化され署名された `.tscfg` パッケージです。現在、パッケージの作成と検査は可能ですが、一般的な構成アプリケーションは未完成です。実稼働フリートの構成、災害復旧、または設定が変更されたことの受け入れチェックにはこれに依存しないでください。

### 6.1 コントロールの機能

| アクション | 現在の結果 |
|---|---|
| デバイス証明書のエクスポート | 送信者がこのデバイスのパッケージを作成できるように公開証明書を提供します。秘密鍵をエクスポートしません |
| 検証のみ | 構造と暗号文の署名を、含まれている証明書と照合してチェックします。署名者の信頼や受信者の身元を確立しません |
| パッケージを選択または貼り付けた後にインポート | フロントエンドとバックエンドのパラメーターがまだ一致していません。このフローは完了できません |
| パッケージリストからインポート | 既存のデバイス ファイルをコピー、復号化、または適用せずに検証します。 |
| 適用 | 設定を書き込まずにモジュール名を復号化してリストします。まだ成功を報告する可能性があります |
| Developer デバイス上で Config Pack をエクスポート | ダウンロード可能なパッケージを作成し、それを SD カードに保存しようとします。 |

### 6.2 送信元と受信者を確認してください

検証は現在、証明書チェーンの信頼を確立せずに、パッケージに含まれる署名者証明書を使用します。署名は暗号文をカバーします。表示されるすべてのフィールドが認証されていると想定しないでください。公式ラベルは信頼できる情報源の証明ではありません。

アセット システムまたは独立した信頼できるチャネルを使用して、署名者の指紋、ターゲット デバイス証明書、およびパッケージの目的を確認します。プレビューのターゲット名は、証明書のフィンガープリント チェックに代わるものではありません。同じメッセージで証明書とフィンガープリントを受信することは、独立したチェックではありません。

### 6.3 デバイス証明書を共有し、パッケージを検査します

**このデバイスの証明書を提供するには:** [デバイス証明書のエクスポート] を選択し、完全な PEM と表示されたフィンガープリントをコピーします。公開証明書を送信者に送信し、別の信頼できるチャネルを通じてそのフィンガープリントを確認します。

**受信したパッケージを検査するには:** [インポート Config Pack] を開き、`.tscfg` ファイルを選択または貼り付けて、[検証のみ] を選択します。署名者の詳細を確認し、ソースを確認します。検証では、設定が適用されることも、このデバイスが受信者であることも証明されることもありません。ソース、ターゲット、目的が不明瞭な場合は中止してください。

検証に合格した後でも、現在の一般的なインポートおよび適用コントロールを使用してデバイスを構成することはできません。関連する機能ページでサポートされているコントロールを使用し、結果の設定を確認します。

### 6.4 Developer デバイスからのエクスポート

1. 有効な JSON 設定ファイルを SD カード上に準備し、検証済みのターゲット証明書を取得します。
2. [Config Pack のエクスポート] を選択し、ファイルを選択し、名前と説明を入力して、受信者デバイスの証明書を貼り付けます。
3. パッケージを生成し、[ダウンロード] を選択して、ブラウザーが `.tscfg` ファイルを保存したことを確認します。
4. ダウンロードと`/sdcard/output_config/`配下のファイルを別々に確認してください。 SD の書き込みが失敗した場合でも、パッケージは引き続きダウンロードできる場合があります。

エクスポートではソース設定は変更されません。間違った受信者向けに作成されたパッケージ、または置き換えられた受信者証明書を再生成します。エクスポートが成功しても、受信デバイス上の一般的なアプリケーションが動作していることは確認されません。

## 7。トラブルシューティングとインシデント対応

### 7.1 よくある問題

| の症状 | どうすればいいですか |
|---|---|
| アカウントのセキュリティがありません | root にのみ表示されます |
| キー ID が取られているか長すぎます | 短い未使用の ID を選択します。セクション 3.1 を参照してください。 |
| 鍵生成は未確認 | 待って、レコードを調べます。同じIDを再送信しないでください |
| デプロイは完了しましたが、レコードが見つからないか、テストが失敗しました | リモート認証、ローカル レコード、サインインを個別に確認します。セクション 3.3 を参照してください。 |
| 指紋の確認または変更が表示されます | 信頼できるチャネルを信頼するかどうかを決定する前に、そのチャネルを通じて検証してください。セクション 4.3 を参照してください。 |
| 失効後もローカルレコードが残る | リモート結果を確認し、ローカル削除の失敗とサービス参照を処理します |
| ホストを削除した後もアクセスは引き続き機能します | 削除はローカル レコードにのみ影響します。リモート公開鍵を個別に取り消す |
| 証明書は保存されていますが、HTTPS は停止しています | デバイスの時間を確認し、表示された認証情報または起動の問題を確認します |
| 実行中のサービスはまだ古い証明書を使用しています | 指示に従って再起動し、アクティブな証明書を確認します。 |
| クライアントが証明書を拒否しました | クライアントの信頼性、アクセス名、許可された使用法、および有効性を確認します |
| 適用は成功しますが、設定は変更されません | 一般的なアプリケーションはモジュール設定をまだ書き込んでいません。機能ページから設定を行う |

### 7.2 キーまたはパスワードの漏洩の疑い

1. デバイスおよび影響を受けるマテリアルへのアクセスを制限します。調査に必要な記録を保管します。
2. 公開された SSH 秘密キーの場合は、信頼できる接続を通じて、影響を受けるすべてのサーバーでその公開キーを取り消します。バックアップをチェックし、古いキーが機能しなくなっていることを確認します。
3. 新しい ID で新しい RSA キーを作成して展開します。それを確認してから、古いキーとエクスポートされたコピーを削除します。
4. 公開された SSH パスワードの場合は、信頼できる管理接続を通じてパスワードを変更し、サインイン レコードを確認します。
5. 公開された HTTPS キーの場合は、セクション 5.6 の説明に従って資格情報を置き換え、失効および古いパッケージに関して CA 管理者と協力します。

ローカル ホスト リストは、アクセスを許可したすべてのサーバーをカバーしているとは限りません。サーバーと資産の記録も確認してください。ログを共有する前に、ユーザーが入力したパスワード、キー、その他の機密コンテンツがないか確認してください。

### 7.3 現在の動作限界

HTTP 管理、不完全な集中認証、初期展開時の自動信頼、および Config Pack 制限用のアカウント。 Hidden はアクセス制御メカニズムではありません。

レビューされたビルド構成では、NVS 暗号化、フラッシュ暗号化、またはセキュア ブートが有効になっていません。これらが保存されたキーや起動時の整合性を保護するとは考えないでください。フラッシュされたファームウェア構成とハードウェア セキュリティ設定は個別にチェックする必要があります。対象の環境がこれらの制限を許容できない場合は、セキュリティ所有者に隔離または修正を手配するよう依頼してください。

## 8。バージョンメモと用語集

### 8.1 このエディションの範囲

本ガイドは、2026 年 10 月 9 日に確認した TianShanOS 0.6.1 のコードと中英の画面に基づいています。後続の版でも、変更されていない機能には引き続き参照できます。画面、手順、メッセージが違う場合は、使用中の版のリリース ノートを確認してから操作してください。

レビューでは、ソース コードとローカルでシミュレートされたインターフェイスが取り上げられました。シミュレーションはハードウェア上の受け入れテストとして扱われませんでした。ここで説明されているように、独自の環境で SSH アクセス、TLS ハンドシェイク、再起動、およびリモート認証を確認してください。

### 8.2 このガイドで使用される用語

- **公開キー / 秘密キー:** アクセスを許可する管理者と公開キーを共有します。秘密鍵を秘密にしておきます。認証には一致するペアが使用されます。
- **フィンガープリント:** サーバーまたは証明書の ID を比較するために使用されるダイジェスト。比較する前に、異なる表示形式を変換します。
- **CSR / CA:** 証明書署名リクエスト、および認証局またはその証明書。
- **CN / O / OU:** 証明書サブジェクトの共通名、組織、および組織単位。フォーム内の部門は OU に対応します。
- **SAN / EKU:** 証明書がカバーするアクセス名または IP アドレス、および許可される認証目的。
- **PEM:** 証明書、CSR、およびキーの BEGIN/END マーカーを含むテキスト形式。
- **mTLS / PKI:** 相互証明書認証、および証明書と信頼管理システム。
- **NVS:** デバイス設定とキー用のフラッシュ ストレージ領域。その名前は暗号化を意味するものではありません。
