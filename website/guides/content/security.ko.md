# TianShanOS 보안 페이지 가이드

이 가이드에서는 TianShanOS 0.6.1의 기능과 인터페이스에 대해 설명합니다. 해당 기능이 변경되지 않은 이후 버전에서는 여전히 유용할 수 있습니다. 버전 번호가 다르다고 해서 가이드가 자동으로 쓸모 없게 되는 것은 아닙니다. 인터페이스, 단계 또는 결과 메시지가 다른 경우 계속하기 전에 설치된 버전의 릴리스 노트를 확인하세요.

이 가이드를 사용하여 장치 비밀번호를 변경하고, SSH 액세스를 설정하고, 서버 ID를 확인하고, 인증서를 관리하세요. 처음 설정하는 경우 1, 2 및 3 장부터 시작하세요. 인증서 및 Config Pack 절차는 해당 기능을 담당하는 관리자를 위한 것입니다.

> 신뢰할 수 있는 관리 네트워크를 사용합니다. 전체 웹 인터페이스는 현재 HTTP를 사용하며 대부분의 API 작업에는 중앙 집중식 로그인 및 권한 적용이 부족합니다. 제어된 관리 네트워크에 장치를 유지합니다. HTTPS 인증서를 설치해도 전체 웹 인터페이스가 HTTPS로 전환되지는 않습니다.

## 1. 시작하기 전에

### 1.1 필요한 작업 찾기

| 작업 | 어디로 가야합니까? |
|---|---|
| 장치의 root 또는 admin 비밀번호 변경 | 계정 보안; 2 장 |
| SSH 키를 사용하여 서버에 연결 | 키 관리 및 배포된 호스트; 3 장 |
| 키 복사 또는 서버 ID 확인 | 키 관리 및 알려진 호스트 지문; 4 장 |
| 인증서 및 상호 인증 설정 | HTTPS 인증서; 5 장 |
| Exchange 암호화 구성 패키지 | Config Pack; 6 장. 일반 구성 적용이 아직 완료되지 않았습니다. |

### 1.2 계정 및 장치 ID

- **admin**는 보안을 열고 키, 호스트, 인증서 및 Config Pack 컨트롤을 볼 수 있지만 계정 보안은 볼 수 없습니다.
- **root**는 root 및 admin 비밀번호를 설정하거나 admin를 기본 비밀번호로 재설정할 수도 있습니다. 이러한 비밀번호 관리 작업은 root 인증을 확인합니다.
- A **Developer 장치**는 장치 인증서의 조직 단위(OU)로 식별됩니다. 이는 장치 ID입니다. 현재 이러한 장치만 구성 팩 및 SSH 호스트 구성을 내보낼 수 있습니다. root로 로그인해도 변경되지 않습니다.

표시되는 버튼은 해당 API가 액세스 권한을 적용한다는 것을 설정하지 않습니다. 인증 자체를 확인하는 비밀번호 관리 등의 작업과는 별도로, 현재는 신뢰할 수 있는 관리 네트워크를 통해 접근을 제한해야 합니다.

### 1.3 작업 준비

1. 브라우저의 IP 주소가 의도한 장치에 속해 있는지, 컴퓨터가 신뢰할 수 있는 관리 네트워크에 있는지 확인하세요.
2. SSH 주소, 포트, 사용자 이름을 서버 관리자에게 확인하세요.
3. 페이지를 통해 공개 키를 배포하거나 취소하려면 원격 계정의 비밀번호와 비밀번호 인증이 필요합니다. 서버 관리자는 나중에 비밀번호 인증을 활성화 상태로 둘지 여부를 결정합니다.
4. 액세스를 취소하거나 키를 삭제하거나 인증서를 교체하기 전에 다른 관리 연결(서버 콘솔, 다른 관리자 키 또는 장치의 HTTP 인터페이스)이 작동하는지 확인하세요.

## 2. 장치 비밀번호 변경

이 컨트롤은 TianShanOS 로그인 비밀번호를 변경합니다. 원격 서버의 SSH 비밀번호는 변경되지 않습니다.

### 2.1 처음 로그인 후 프롬프트

계정에 여전히 비밀번호가 변경되지 않은 것으로 표시된 경우 로그인 후 비밀번호 변경 프롬프트가 나타납니다. 길고 고유한 비밀번호를 설정하세요. 나중에 변경하도록 선택하면 비밀번호를 변경하지 않고 프롬프트가 닫힙니다.

프롬프트는 언제든지 다시 열 수 있는 계정 설정 화면이 아닙니다. admin가 이미 비밀번호를 변경했고 또 다른 변경이 필요한 경우 root는 보안에서 비밀번호를 설정할 수 있습니다.

### 2.2 비밀번호를 root로 설정하세요.

1. root로 로그인하고 탐색 모음에서 보안을 엽니다.
2. 계정 보안에서 root 또는 admin 비밀번호 제어를 찾으세요. 새 비밀번호와 확인을 입력하세요.
3. root 비밀번호 설정 또는 admin 비밀번호 설정을 선택합니다. 인터페이스는 4-64 문자를 허용합니다. 기술적 최소값은 4자입니다. 길고 고유한 비밀번호를 사용하세요.

**결과 확인:** 원래 세션에서 로그아웃하기 전에 개인 탐색 창에서 새 비밀번호로 로그인하세요. 새 비밀번호를 설정해도 기존 세션이 자동으로 종료되지는 않습니다.

**로그인에 실패한 경우:** 먼저 계정과 기기 주소를 확인하세요. 5번 연속 실패한 시도는 약 5분간의 잠금을 유발합니다. 반복적인 추측을 피하세요.

### 2.3 admin 비밀번호 재설정

루트는 admin를 기본값으로 재설정을 선택하여 `rm01`에 대한 비밀번호를 복원하고 로그인 잠금을 지울 수 있습니다. 새 세션에서 admin로 로그인한 후 즉시 고유 비밀번호를 설정하세요.

> 일시적으로 액세스를 복구하는 경우에만 기본 비밀번호를 사용하십시오. 즉시 변경하고 더 이상 필요하지 않은 세션에서 로그아웃하세요.

## 3. SSH 키를 사용하여 서버에 연결

초기 설정을 위해 RSA 키를 생성하고, 공개 키를 배포하고, 결과를 검토하고, 연결을 테스트합니다. 이 프로세스의 일부로 서버 지문을 확인하십시오. 키를 폐기하는 경우 먼저 모든 서버에서 액세스 권한을 취소하고 이전 키가 더 이상 작동하지 않는지 확인한 후 기기에서 삭제하세요.

### 3.1 키 생성

1. 키 관리에서 새 키 생성을 선택합니다.
2. `backup01`처럼 사용하지 않는 키 ID를 정하세요. 쉼표 없이 영문과 숫자를 짧게 조합하고 10자 이내로 입력하세요. 실제 제한은 10 UTF-8 바이트입니다. ASCII가 아닌 문자는 한 글자에 1바이트보다 많은 공간을 쓸 수 있습니다.
3. RSA 2048 또는 RSA 4096를 선택합니다. RSA 2048가 기본값입니다. ECDSA 옵션이 표시되지만 현재 SSH 워크플로는 이를 지원하지 않습니다. SSH의 경우 RSA를 선택하세요.
4. 유용한 경우 설명이나 별칭을 추가하세요. 개인 키를 백업하거나 마이그레이션해야 하는 경우에만 내보내기 가능을 켜십시오. 나중에 이 옵션을 변경할 수 있는 페이지 컨트롤이 없습니다.
5. 필요한 경우 숨김을 설정한 다음 생성을 선택합니다. 이 옵션은 목록 표시에 영향을 미칩니다. 실제 키 ID를 비밀로 유지하지 않습니다.

**결과 확인:** 완료 후 창이 닫히고 목록이 새로 고쳐집니다. 원하는 ID와 RSA 유형을 찾은 다음 공개 키를 엽니다. 전체 텍스트가 `ssh-rsa`로 시작하는지 확인하세요.

**생성을 기다리는 동안:** 다시 제출하지 마세요. 창을 닫아도 장치의 생성 작업은 취소되지 않습니다.

| 메시지 또는 상황 | 수행할 작업 |
|---|---|
| 이미 사용중인 아이디입니다 | 다른 ID를 선택하세요. 이제 새 키 워크플로는 키를 덮어쓰는 대신 기존 ID를 거부합니다. |
| 키 개수 제한에 도달했습니다. | SSH 키는 최대 8개까지 저장할 수 있습니다. 사용하지 않는 키를 정리하려면 먼저 접근 권한 철회 절차를 진행하세요. |
| 스토리지 또는 메모리가 부족합니다. | 다시 시도하기 전에 장치 리소스 문제를 해결하십시오. 실패를 성공적인 창조로 여기지 말라 |
| 키가 생성되었지만 목록을 새로 고칠 수 없습니다. | 수동으로 새로 고치고 키를 확인하세요. 다시 생성하지 마세요 |
| 세대는 확인되지 않았습니다. | 장치가 여전히 작동 중일 수 있습니다. 기다렸다가 기록을 확인하세요. 동일한 ID를 다시 제출하지 마세요 |
| 정리가 완료되지 않았습니다. | 장치 저장 공간을 확인하고, 필요한 경우 관리자를 참여시키고, 추가 키 생성을 일시 중지합니다. |

동일한 ID의 레코드를 찾는 것은 해당 레코드가 존재한다는 것만 증명합니다. 결과가 확인되지 않은 경우 작업이 완료된 것으로 처리하기 전에 의도한 키인지 확인하세요.

### 3.2 공개 키 배포

배포는 원격 계정의 `~/.ssh/authorized_keys`에 공개 키를 추가하여 해당 계정이 일치하는 개인 키를 허용하도록 합니다. 서버 비밀번호는 변경되지 않습니다.

1. 의도한 키 행에서 배포를 선택합니다.
2. 서버 주소, 사용자 이름, SSH 포트 및 SSH 로그인 비밀번호를 입력합니다.
3. 주소와 계정을 검토한 다음 배포 시작을 선택합니다.
4. 결과를 읽고 배포된 호스트에서 해당 레코드를 확인합니다.

> 새 버전은 비밀번호 인증 전에 호스트 지문을 확인하고, 등록된 호스트의 지문이 바뀌면 연결을 거부합니다. 다만 공개 키를 처음 배포할 때는 확인을 요청하지 않고 미등록 호스트의 지문을 저장해 신뢰합니다. 첫 배포는 관리된 네트워크에서 진행하고, 신뢰할 수 있는 별도 경로로 전체 지문을 대조하세요.

### 3.3 배포 결과 이해

| 결과가 말해 주는 것 | 다음에 수행할 작업 |
|---|---|
| 키가 배포되었고, 호스트가 등록되었으며, 공개 키 로그인이 확인되었습니다. | 호스트 세부 정보를 확인한 후 실행해야 하는 실제 작업을 테스트하세요. |
| 키가 배포되고 호스트가 등록되었지만 로그인이 확인되지 않았습니다. | 선택 테스트. 실패할 경우 다른 관리 연결을 통해 원격 인증 및 계정 설정을 확인하세요. |
| 키가 배포되었지만 등록이 실패했거나 확인되지 않았습니다. | 다시 배포하기 전에 로컬 목록과 원격 인증을 확인하세요. |
| 배포가 완료되었지만 목록을 새로 고칠 수 없습니다. | 수동으로 새로 고칩니다. 목록 새로 고침이 실패했다고 해서 원격 키가 설치되지 않았다는 의미는 아닙니다. |

**결과가 불완전하므로 반복적으로 배포하지 마십시오.** 배포할 때마다 키가 추가되고 중복 항목이 생성될 수 있습니다. 원격 결과를 확인해야 할 경우 다른 관리 연결을 사용하여 `authorized_keys`를 검사하세요.

### 3.4 연결 테스트

1. 배포된 호스트에서 주소, 포트, 사용자 이름, 키 ID를 확인한 후 테스트를 선택합니다.
2. 호스트 지문 확인이 나타나면 신뢰 및 연결을 선택하기 전에 4.3 섹션에 설명된 대로 신뢰할 수 있는 지문을 얻고 비교하십시오.
3. 연결 후 장치는 고정 에코 명령 `echo "TianshanOS SSH Test OK"`를 시도합니다.

**성공의 의미:** 테스트 페이지에서는 원격 명령의 종료 상태나 출력이 아니라 요청 성공 여부를 계속 확인합니다. 기본적인 연결 확인으로 활용하세요. 중요한 작업의 경우 실제 출력, 종료 상태 및 권한을 확인합니다. 또한 이 테스트에서는 sudo 또는 기타 애플리케이션 명령이 작동하는지 확인하지 않습니다.

**실패할 경우:** 연결, SSH 서비스, 계정 및 원격 공개 키 인증을 확인하세요. 지문이 변경되거나 서버의 ID가 확실하지 않은 경우 재시도를 중지하세요.

### 3.5 로컬 키를 삭제하기 전에 액세스 권한을 취소하세요.

1. 다른 서버 관리 연결이 작동하고 원래 키가 장치에 남아 있는지 확인하십시오.
2. 호스트 행에서 취소를 선택하고 서버 비밀번호를 입력한 후 취소 및 제거를 확인합니다. 키 행에서 시작하여 대상 세부정보를 입력할 수도 있습니다.
3. 결과를 읽은 다음 신뢰할 수 있는 연결을 사용하여 공개 키와 모든 중복 항목이 `authorized_keys`에서 사라졌는지 확인하세요. 이전 키가 더 이상 작동하지 않는지 확인하세요.
4. 취소는 `authorized_keys.bak` 백업을 남깁니다. 나중에 이전 인증이 복원되지 않도록 서버의 백업 정책에 따라 처리하십시오.
5. 로컬 호스트 레코드가 제거되었는지 확인하십시오. 이제 페이지에서 이 요청을 확인합니다. 원격 취소에 성공했지만 로컬 제거에 실패한 경우 로컬 정리를 별도로 새로 고치고 처리합니다.
6. 모든 대상 서버가 처리된 후에만 이전 키와 불필요한 개인 키 복사본을 삭제해야 합니다.

**일치하는 공개 키가 없는 경우:** 로컬 레코드만 제거하도록 선택하기 전에 계정이 정확하고 서버에 키가 없는지 확인하세요.

**호스트를 제거할 수 없는 경우:** 서비스가 기록을 사용하거나 보호하고 있을 수 있습니다. SSH 명령 또는 관련 자동화 설정에서 서비스 상태 및 참조를 확인하세요. 다시 시도하기 전에 서비스 중지 또는 참조 확인을 완료하세요. 불확실한 상태를 확인하려면 관리자에게 문의하세요.

**해지가 실패로 보고되는 경우:** 실패한 단계를 식별합니다. 로컬 정리에 실패하더라도 원격 키가 이미 사라졌을 수 있습니다. 서버의 인증과 실제 로그인 확인을 사용하여 원격 결과를 설정합니다. 이 문제가 해결될 때까지 로컬 키를 보관하십시오.

## 4. 키, 호스트, 지문 관리

### 4.1 공개 키 복사 또는 개인 키 내보내기

**공개 키:** 공개 키를 선택하고 서버 관리자를 위한 전체 한 줄 값을 복사합니다. 이것은 공개 자료입니다. 잘못된 사람에게 보내면 개인 키가 노출되지 않습니다. 관리자가 계정의 인증 목록에 이를 추가하면 접근 권한이 부여됩니다.

**개인 키:** 내보내기는 생성 중에 내보내기 가능이 활성화된 경우에만 사용할 수 있습니다. 신뢰할 수 있는 컴퓨터와 격리된 관리 네트워크에서 개인 키를 선택하세요. 승인된 비밀 저장소에 저장하고 임시 클립보드를 지우고 사본을 다운로드하세요. 절대로 채팅, 티켓, 로그에 붙여넣지 마세요.

**복사가 아무 작업도 수행되지 않는 경우:** 브라우저는 HTTP 페이지에서 클립보드 액세스를 제한할 수 있습니다. 텍스트를 수동으로 선택하고 복사한 다음 경계 표시와 완전성을 확인하세요. 복사를 활성화하기 위해 브라우저 보안 설정을 약화시키지 마십시오.

### 4.2 취소, 제거 및 삭제

| 액션 | 효과 |
|---|---|
| 공개 키 취소 | 서버 인증을 제거하려고 시도합니다. 원격 비밀번호가 필요합니다 |
| 호스트 제거 | 서버 액세스를 취소하지 않고 로컬 연결 기록을 삭제합니다. |
| 키 삭제 | 서버에 접속하거나 액세스 권한을 취소하지 않고 로컬 키 자료를 삭제합니다. |
| 호스트 지문 제거 | 연결 기록이나 원격 인증이 아닌 저장된 서버 ID 기록을 삭제합니다. |

배포 호스트는 서버 인증의 실시간 보기가 아닌 로컬 목록입니다. 빈 목록은 액세스가 제거되었음을 증명하지 않으며 나열된 호스트에 도달할 수 있다고 보장되지 않습니다.

### 4.3 SSH 서버 지문 확인

지문은 연결 중인 서버를 식별합니다. 이 페이지는 SHA-256 다이제스트를 64 16진수 문자로 저장합니다. OpenSSH 도구는 일반적으로 `SHA256:base64`를 표시합니다. 비교하기 전에 동일한 형식에 대해 관리자에게 문의하십시오. 문자열은 직접 비교할 수 없습니다.

**초기 배포 후:** 알려진 호스트 지문 아래에서 보기를 선택하고 전체 값을 서버 콘솔, 자산 인벤토리 또는 다른 신뢰할 수 있는 채널에서 얻은 값과 비교합니다. 표에는 첫 번째 32 문자만 표시되어 있어 전체 확인에는 충분하지 않습니다.

**테스트에서 확인을 요청하는 경우:** 대화 상자에 현재 전체 지문이 표시됩니다. 신뢰 및 연결을 선택하기 전에 독립적으로 확인하세요. 변경된 경우 서버 ID, IP, 포트, 유지 관리 기록도 확인하세요. 단순히 대화 상자가 나타났다는 이유로 승인하지 마십시오.

**지문이 다르거나 출처가 불분명한 경우:** 연결을 취소하고 조사해 보세요. 이전에 신뢰할 수 없는 연결을 통해 비밀번호를 사용한 경우 잠재적으로 노출된 것으로 간주하십시오. 신뢰할 수 있는 연결을 통해 변경하고, 로그인 로그를 검토하고, 원치 않는 인증을 제거하세요. 접근 권한을 취소하기 위해 의심스러운 연결을 통해 비밀번호를 보내지 마세요.

**승인된 재구축 또는 호스트 키 변경 후:** 먼저 새로운 전체 지문 및 유지 관리 기록을 확인하세요. 확인되면 테스트 확인 대화 상자에서 이를 수락합니다. 또는 이전 항목을 제거하고 다시 테스트한 후 확인된 지문을 확인하세요. 이제 테스트 경로에는 명시적인 확인이 필요합니다. 다시 연결하면 새 키가 자동으로 신뢰될 것이라고 가정하지 마십시오.

**SD 카드 보호:** 알려진 호스트 지문은 카드의 일반 텍스트 JSON와 동기화됩니다. 시작 시 사용 가능한 SD 지문 구성이 해당 로컬 레코드를 대체합니다. 이 파일은 서명되지 않았습니다. 신뢰할 수 없는 변경을 허용하지 마십시오.

### 4.4 SSH 호스트 구성 가져오기 및 내보내기

이 전용 `.tscfg` 워크플로는 주소, 포트, 사용자 이름, 인증 유형 및 키 ID를 저장합니다. SSH 비밀번호나 개인 키가 포함되어 있지 않으며 원격 액세스를 허용하지 않습니다. 6 장의 미완성 일반 응용 프로그램과 별개입니다.

**내보내려면:** Developer 장치에서 호스트 행에서 내보내기를 선택합니다. 다른 장치의 경우 해당 인증서를 제공 및 확인하고, 패키지를 생성하고, 다운로드를 선택합니다. 파일이 저장되었는지 확인하세요. 일반 장치에서는 컨트롤이 표시될 수 있지만 내보내기 요청이 거부됩니다.

**가져오려면:**

1. 패키지가 이 장치용으로 제작되었는지, SD 카드에 쓰기 가능하고 소스가 신뢰할 수 있는 채널을 통해 확인되었는지 확인하세요.
2. 이 장치에 올바른 참조 키가 있는지 확인하세요. 일치하는 ID만으로는 충분하지 않습니다. 키 자료는 서버의 인증과 일치해야 합니다.
3. 호스트 가져오기를 선택하고 파일을 선택한 다음 미리보기를 검토합니다. 동일한 이름의 구성을 대체하려는 경우에만 덮어쓰기를 활성화하십시오.
4. 메시지가 나타나면 확인하고 다시 시작하세요. 가져오기는 먼저 패키지를 SD 카드에 저장합니다. 다시 시작할 때 로드 및 암호 해독이 시도됩니다.
5. 시작 로딩이 완료되도록 허용하고, 호스트 목록을 새로 고치고, 주소, 계정, 포트 및 키를 확인한 다음 테스트합니다.

미리보기에 성공해도 서명자를 신뢰할 수 있는지, 이 장치가 수신 대상인지는 확인되지 않습니다. 수신 대상 지문은 로드할 때 확인합니다. 시작 시 호스트 설정을 병합하고 관계없는 로컬 기록은 유지합니다. 패키지 하나를 가져와도 기존 목록 전체가 삭제되지는 않습니다.

잘못된 레코드를 제거하고 해당 SD 구성이 지워졌는지 확인하세요. 다시 시작한 후에 나머지 패키지를 다시 로드할 수 있습니다. 레코드가 사용 중인 경우 서비스 참조를 확인합니다. 장치 인증서를 교체하기 전에 5.6 섹션도 읽어보세요.

## 5. HTTPS 인증서 및 mTLS 구성

포트 443의 현재 서비스는 전체 웹 인터페이스가 아닌 상태, ID 및 권한 테스트 엔드포인트를 제공합니다. 기본 시작에는 장치 키, 장치 인증서, 클라이언트 CA 체인 및 유효한 장치 시계가 필요합니다.

### 5.1 어떤 인증서가 무엇을 하는지 알아보세요.

- **장치 인증서 및 개인 키**를 사용하면 장치가 클라이언트에게 자신의 신원을 증명할 수 있습니다.
- 컴퓨터나 서비스가 보유한 **클라이언트 인증서 및 개인 키**를 통해 클라이언트는 장치에 자신의 신원을 증명할 수 있습니다.
- **장치의 클라이언트 확인 CA**는 클라이언트 인증서의 유효성을 검사합니다. 컴퓨터나 브라우저가 장치 인증서를 자동으로 신뢰하도록 만들지는 않습니다.

이 양방향 인증을 상호 TLS 또는 mTLS라고 합니다. 클라이언트는 여전히 장치 인증서의 발급 CA를 신뢰하고 해당 액세스 이름, 허용된 용도 및 유효성을 확인해야 합니다.

### 5.2 상태 읽기 및 장치 시간 설정

저장됨, 유효 기간 내 및 HTTPS: 실행 중은 저장, 시간 유효성 및 서비스 운영을 별도로 설명합니다. 하나는 다른 것을 확립하지 않습니다.

| 상태 또는 상황 | 수행할 작업 |
|---|---|
| 장치 인증서, 개인 키 또는 클라이언트 확인 CA가 누락되었습니다. | 다음 섹션을 사용하여 누락된 자격 증명을 설치합니다. |
| 장치 시간을 기다리는 중 | 컴퓨터의 시계가 올바른지 확인한 다음 이 컴퓨터에서 장치 시간 설정(브라우저 소스)을 선택합니다. |
| 아직 유효하지 않거나 만료됨 | 장치 시계 및 인증서 날짜를 확인하십시오. 만료된 경우 갱신 준비 |
| 유효기간 내이지만 HTTPS가 실행되고 있지 않습니다. | 표시된 자격 증명 누락, 키 불일치 또는 시작 오류를 읽습니다. 해결하고 새로고침하세요 |
| 실행 중인 서비스는 여전히 이전 자격 증명을 사용합니다. | 다른 작업을 저장하고 장치를 다시 시작하십시오. 새 자격 증명이 시작 요구 사항을 충족하고 사용 중인지 확인하세요. |
| 저장 또는 상태가 확인되지 않음 | 새로고침하고 확인합니다. 지시가 있으면 다시 시작하십시오. 반복적인 설치 또는 삭제 방지 |

시간을 설정한 후 표시되는 장치 시간과 동기화 상태를 확인하세요. 서비스가 실행되고 있지 않을 때 자격 증명 및 시간 요구 사항이 충족되면 시스템은 시작을 시도합니다. 계속 중지된 경우 설치가 준비되었다는 증거로 간주하기보다는 표시된 이유를 조사하십시오.

### 5.3 장치 키 및 인증서 요청 생성

1. 키 쌍 생성을 선택합니다. 이렇게 하면 SSH 키와 관련되지 않은 별도의 ECDSA P-256 개인 키가 생성됩니다. 이 인터페이스를 통해 내보낼 수 없습니다.
2. 키가 이미 존재하는 경우 먼저 5.6 섹션을 읽으십시오. 계속하면 덮어쓰게 됩니다.
3. CSR 생성을 선택합니다. 장치 ID(CN), 조직, 부서를 입력하거나 모든 필드를 비워 둡니다. 부서는 인증서의 조직 단위(OU)에 해당합니다.
4. 인증서 서명 요청 생성을 선택하고 전체 CSR 텍스트를 CA 관리자에게 보냅니다.

**짧고 안정적인 장치 ID를 사용하세요.** 영문자와 숫자는 63바이트 UTF-8 제한 내에서 유지하는 것이 가장 쉽습니다. ASCII가 아닌 문자는 여러 바이트를 사용할 수 있습니다. 인터페이스가 길이 오류를 보고하는 경우 필드를 줄이십시오.

**발급 전 이름 확인:** 사용자 정의 필드 경로는 SAN을 생성하지 않습니다. 모든 필드가 비어 있으면 CN은 `TIANSHAN-DEVICE-001`로 고정됩니다. 현재 IP는 사용 가능한 경우에만 IP SAN으로 추가됩니다. DNS SAN이 추가되지 않습니다. CA 관리자가 제어된 발급 프로세스를 사용하여 최종 인증서에 실제 IP 또는 DNS 이름과 필요한 인증 목적을 포함하도록 하십시오. 이 양식에서는 SAN을 편집할 수 없습니다.

CSR에는 개인 키가 없으며 인증서를 설치하지 않습니다. 발급 전에 CA 관리자에게 공개 키, 주제, SAN을 검사하도록 하세요.

### 5.4 장치 인증서 설치

1. 현재 장치 개인 키와 일치하는 PEM 인증서를 얻습니다.
2. 인증서 설치를 선택하고 경계 표시를 포함한 전체 텍스트를 붙여넣은 다음 설치를 선택합니다.
3. 저장된 결과, 인증서 유효성, 실제 HTTPS 상태를 확인하세요. 제목, 발급자, 날짜를 검토하세요.

설치는 형식과 키 쌍을 확인합니다. 새로운 상태 표시는 시간 유효성과 시작 요구 사항도 보고하지만 클라이언트는 여전히 신뢰 체인, 액세스 이름 및 허용된 용도를 확인해야 합니다.

키가 일치하지 않으면 현재 CSR에 대해 발급된 인증서를 찾으세요. 오류를 해결하기 위해 개인 키를 다시 생성하지 마십시오. 결과가 확인되지 않은 경우 새로고침하여 저장된 내용을 확인한 후 재시도 여부를 결정하세요.

### 5.5 클라이언트 CA 체인을 설치하고 테스트합니다.

1. CA 설치를 선택하고 클라이언트를 신뢰하는 데 사용되는 하나 이상의 PEM CA 인증서를 붙여넣은 다음 설치를 선택합니다.
2. 상태를 확인하세요. 중지된 서비스는 자격 증명과 시간이 준비되면 시작을 시도합니다. 실행 중인 서비스가 변경된 자격 증명을 보고하는 경우 이를 적용하라는 지침에 따라 다시 시작하세요.
3. 올바른 목적과 역할을 가진 신뢰할 수 있는 클라이언트 인증서를 사용하여 적절한 테스트 엔드포인트에 액세스합니다.
4. 신뢰할 수 없는 인증서 또는 인증서 없음을 사용하여 반복하고 거부를 확인합니다.

**결과 확인:** HTTPS가 실행 중이며 원하는 인증서를 사용합니다. 활성 인증서 SHA-256가 표시되면 해당 지문을 비교하세요. 신뢰할 수 있는 클라이언트는 자신의 역할이 허용하는 엔드포인트에만 액세스해야 합니다. 신뢰할 수 없는 클라이언트는 연결하면 안 됩니다. 실제 장치에서 이러한 결과를 확인하십시오.

### 5.6 인증서 갱신 또는 모든 자격 증명 삭제

**인증서 만료:** 손상되지 않은 키를 재사용하여 새 인증서를 요청하고 설치한 후 상태 지침에 따라 적용하고 다시 테스트합니다. 구성 팩은 수신자 인증서 지문과 연결되어 있습니다. 동일한 키를 사용하더라도 인증서가 변경되었기 때문에 다시 초기화하거나 다시 시작한 후에 이전 패키지가 거부될 수 있습니다. 교체 패키지를 미리 준비하십시오.

**개인 키 교체:** 기존 CSR 및 인증서가 더 이상 새 키와 일치하지 않습니다. 이는 CA의 이전 인증서를 취소하지 않습니다. 노출된 키는 CA 관리자와 별도로 처리하세요. 분실된 키에 의존하는 패키지는 복구가 불가능할 수 있습니다.

**모든 자격 증명 삭제:** 자격 증명 삭제는 장치 키, 장치 인증서 및 클라이언트 CA 체인을 함께 제거합니다. HTTP 관리 액세스가 작동하는지 확인하고 먼저 교체 패키지를 준비하세요. 공개 인증서 백업은 개인 키를 복원할 수 없습니다.

삭제 후 장치 인증서 없음 및 자격 증명 누락을 확인하십시오. 실행 중인 HTTPS 서비스는 여전히 이전 자격 증명을 보유할 수 있습니다. 저장된 데이터를 삭제하는 것은 즉시 취소되는 것이 아닙니다. 지시에 따라 다시 시작하고 이전 자격 증명이 더 이상 사용되지 않는지 확인합니다. 새 키, 발급된 장치 인증서, 클라이언트 CA 체인 및 연결 테스트를 통해 서비스를 복원합니다.

## 6. Config Pack 제한 사항 이해

Config Pack는 암호화되고 서명된 `.tscfg` 패키지입니다. 현재 패키지를 생성하고 검사할 수 있지만 일반 구성 적용은 완료되지 않았습니다. 프로덕션 플릿 구성, 재해 복구 또는 설정이 변경된 승인 확인에 의존하지 마십시오.

### 6.1 컨트롤의 기능

| 액션 | 현재 결과 |
|---|---|
| 수출 장치 인증서 | 발신자가 이 장치에 대한 패키지를 생성할 수 있도록 공개 인증서를 제공합니다. 개인 키를 내보내지 않습니다. |
| 확인만 가능 | 포함된 인증서에 대해 구조와 암호문 서명을 확인합니다. 서명자 신뢰 또는 수신자 신원을 설정하지 않습니다. |
| 패키지 선택 또는 붙여넣기 후 가져오기 | 프런트엔드와 백엔드 매개변수가 여전히 일치하지 않습니다. 이 흐름을 완료할 수 없습니다 |
| 패키지 목록에서 가져오기 | 복사, 암호 해독 또는 적용 없이 기존 장치 파일의 유효성을 검사합니다. |
| 적용 | 설정을 쓰지 않고 모듈 이름을 해독하고 나열합니다. 여전히 성공을 보고할 수 있습니다. |
| Developer 장치에서 Config Pack 내보내기 | 다운로드 가능한 패키지를 생성하고 이를 SD 카드에 저장하려고 시도합니다. |

### 6.2 소스와 수신자를 확인하세요.

Verification은 현재 인증서 체인 신뢰를 설정하지 않고 패키지에 포함된 서명자 인증서를 사용합니다. 서명은 암호문을 포함합니다. 표시된 모든 필드가 인증되었다고 가정하지 마십시오. 공식 라벨은 신뢰할 수 있는 출처의 증거가 아닙니다.

자산 시스템 또는 독립적이고 신뢰할 수 있는 채널을 사용하여 서명자 지문, 대상 장치 인증서 및 패키지 목적을 확인합니다. 미리보기의 대상 이름은 인증서 지문 확인을 대체하지 않습니다. 동일한 메시지에서 인증서와 지문을 받는 것은 독립적인 확인이 아닙니다.

### 6.3 장치 인증서 공유 및 패키지 검사

**이 장치의 인증서를 제공하려면** 장치 인증서 내보내기를 선택하고 전체 PEM 및 표시된 지문을 복사합니다. 공개 인증서를 보낸 사람에게 보내고 다른 신뢰할 수 있는 채널을 통해 지문을 확인합니다.

**수신된 패키지를 검사하려면** Config Pack 가져오기를 열고 `.tscfg` 파일을 선택하거나 붙여넣은 다음 확인만을 선택합니다. 서명자 세부정보를 검토하고 출처를 확인하세요. 확인을 통해 설정이 적용되거나 이 장치가 수신자인지 확인되지 않습니다. 출처, 대상, 목적이 불분명하면 중지하세요.

검증을 통과한 후에도 현재의 일반 가져오기 및 적용 컨트롤을 사용하여 장치를 구성할 수 없습니다. 관련 기능 페이지에서 지원되는 컨트롤을 사용하고 결과 설정을 확인하세요.

### 6.4 Developer 장치에서 내보내기

1. SD 카드에 유효한 JSON 구성 파일을 준비하고 검증된 대상 인증서를 얻습니다.
2. Config Pack 내보내기를 선택하고 파일을 선택한 후 이름과 설명을 입력하고 수신 장치 인증서를 붙여넣습니다.
3. 패키지를 생성하고 다운로드를 선택한 후 브라우저가 `.tscfg` 파일을 저장했는지 확인합니다.
4. 다운로드와 `/sdcard/output_config/` 아래의 파일을 별도로 확인하세요. SD 쓰기가 실패하더라도 패키지를 계속 다운로드할 수 있습니다.

내보내기는 소스 설정을 변경하지 않습니다. 잘못된 수신자를 위해 만들어진 패키지 또는 교체된 수신자 인증서를 다시 생성합니다. 내보내기가 성공하더라도 수신 장치의 일반 응용 프로그램이 작동 중이라는 사실은 확인되지 않습니다.

## 7. 문제 해결 및 사고 대응

### 7.1 일반적인 문제

| 증상 | 수행할 작업 |
|---|---|
| 계정 보안이 누락되었습니다 | root에만 표시됩니다. |
| 키 ID가 사용되었거나 너무 깁니다. | 짧고 사용되지 않은 ID를 선택하세요. 섹션 3.1 참조 |
| 키 생성이 확인되지 않았습니다. | 기다렸다가 기록을 검사합니다. 동일한 ID를 다시 제출하지 마세요 |
| 배포가 완료되었지만 기록이 누락되었거나 테스트가 실패했습니다. | 원격 인증, 로컬 기록, 로그인을 별도로 확인하세요. 섹션 3.3 참조 |
| 지문 확인 또는 변경 사항이 나타납니다. | 신뢰하기로 결정하기 전에 신뢰할 수 있는 채널을 통해 확인하세요. 섹션 4.3 참조 |
| 취소 후에도 로컬 레코드가 유지됩니다. | 원격 결과 확인 후 로컬 제거 실패 및 서비스 참조 처리 |
| 액세스가 계속 작동합니다. | 제거는 로컬 레코드에만 영향을 미칩니다. 원격 공개 키를 별도로 취소 |
| 인증서가 저장되었지만 HTTPS가 중지되었습니다. | 장치 시간을 확인한 후 표시된 자격 증명 또는 시작 문제를 확인하세요. |
| 실행 중인 서비스는 여전히 이전 인증서를 사용합니다. | 지시에 따라 다시 시작한 다음 활성 인증서를 확인하십시오. |
| 클라이언트가 인증서를 거부합니다. | 클라이언트 신뢰, 액세스 이름, 허용된 용도 및 유효성을 확인합니다. |
| 적용이 성공했지만 설정이 변경되지 않음 | 일반 애플리케이션은 아직 모듈 설정을 작성하지 않습니다. 기능 페이지를 통해 구성하십시오. |

### 7.2 의심되는 키 또는 비밀번호 노출

1. 장치 및 영향을 받는 자료에 대한 액세스를 제한합니다. 조사에 필요한 기록을 보관합니다.
2. 노출된 SSH 개인 키의 경우 신뢰할 수 있는 연결을 통해 영향을 받는 모든 서버에서 공개 키를 취소합니다. 백업을 확인하고 이전 키가 더 이상 작동하지 않는지 확인하세요.
3. 새 ID로 새 RSA 키를 생성하고 배포합니다. 이를 확인한 다음 이전 키와 내보낸 복사본을 제거합니다.
4. 노출된 SSH 비밀번호의 경우 신뢰할 수 있는 관리 연결을 통해 비밀번호를 변경하고 로그인 기록을 검토하세요.
5. 노출된 HTTPS 키의 경우 5.6 섹션에 설명된 대로 자격 증명을 교체하고 해지 및 이전 패키지에 대해 CA 관리자와 협력하세요.

로컬 호스트 목록에는 액세스 권한을 부여한 모든 서버가 포함되지 않을 수 있습니다. 서버 및 자산 기록도 확인하세요. 로그를 공유하기 전에 사용자가 입력한 비밀번호, 키 또는 기타 민감한 콘텐츠가 있는지 검토하세요.

### 7.3 현재 작동 제한

HTTP 관리, 불완전한 중앙 집중식 인증, 초기 배포 시 자동 신뢰 및 Config Pack 제한 사항을 위한 계정입니다. Hidden은 액세스 제어 메커니즘이 아닙니다.

검토된 빌드 구성은 NVS 암호화, 플래시 암호화 또는 보안 부팅을 활성화하지 않습니다. 이것이 저장된 키나 시작 무결성을 보호한다고 가정하지 마십시오. 플래시된 펌웨어 구성 및 하드웨어 보안 설정에는 별도의 확인이 필요합니다. 의도한 환경에서 이러한 제한을 허용할 수 없는 경우 보안 소유자에게 격리 또는 수정을 요청하세요.

## 8. 버전 노트 및 용어집

### 8.1 이 버전의 범위

이 가이드는 2026년 10월 9일에 확인한 TianShanOS 0.6.1 코드와 중국어·영어 화면을 기준으로 작성했습니다. 이후 버전에서도 기능이 바뀌지 않았다면 참고할 수 있습니다. 화면, 절차, 메시지가 다르면 사용 중인 버전의 릴리스 설명을 확인한 뒤 진행하세요.

검토에서는 소스 코드와 로컬 시뮬레이션 인터페이스를 다루었습니다. 시뮬레이션은 하드웨어에 대한 승인 테스트로 처리되지 않았습니다. 여기에 설명된 대로 사용자 환경에서 SSH 액세스, TLS 핸드셰이크, 다시 시작 및 원격 인증을 확인하세요.

### 8.2 이 가이드에 사용된 용어

- **공개 키/개인 키:** 액세스 권한을 부여한 관리자와 공개 키를 공유합니다. 개인 키를 비밀로 유지하십시오. 인증은 일치하는 쌍을 사용합니다.
- **지문:** 서버 또는 인증서 ID를 비교하는 데 사용되는 다이제스트입니다. 비교하기 전에 다양한 디스플레이 형식을 변환하세요.
- **CSR / CA:** 인증서 서명 요청 및 인증 기관 또는 해당 인증서.
- **CN / O / OU:** 인증서 주체의 일반 이름, 조직 및 조직 단위입니다. 양식의 부서는 OU에 해당합니다.
- **SAN / EKU:** 인증서에 포함된 액세스 이름 또는 IP 주소와 허용된 인증 목적입니다.
- **PEM:** 인증서, CSR 및 키에 대한 BEGIN/END 표시가 있는 텍스트 형식입니다.
- **mTLS / PKI:** 상호 인증서 인증, 인증서 및 신뢰 관리 시스템.
- **NVS:** 장치 설정 및 키를 위한 플래시 저장 영역입니다. 그 이름은 암호화를 의미하지 않습니다.
